# Bybit P2P USDT/TJS

Парсер `bybit_p2p_tjs_green_avg3` читает объявления через официальный
`POST /v5/p2p/item/online`. Он не создаёт сделки и не меняет разрешения аккаунта.
Проверка ключа использует `GET /v5/user/query-api` и показывает только `readOnly`
и разрешения `FiatP2P`. Заголовки авторизации и исходный ответ с данными аккаунта
не выводятся.

Документация: [авторизация](https://bybit-exchange.github.io/docs/p2p/guide),
[объявления](https://bybit-exchange.github.io/docs/p2p/ad/online-ad-list),
[разрешения ключа](https://bybit-exchange.github.io/docs/v5/user/apikey-info).

## Секреты

На Windows пара хранится в отдельном файле DPAPI CurrentUser с закрытым ACL.
Файл находится вне репозитория и ZIP. Диагностический запуск:

```powershell
./scripts/bybit_readonly_windows.ps1 -VaultPath <закрытый-файл-DPAPI> -ContainerName <контейнер-OzarkPay>
```

Расшифрованная пара передаётся дочернему процессу через stdin и существует только
в памяти. Worker получает `BYBIT_P2P_API_KEY` и `BYBIT_P2P_API_SECRET` только
в памяти через защищённый процесс запуска; Windows использует DPAPI → stdin.
Постоянное хранение пары в Docker ENV не используется. Для будущего Linux
нужен отдельный процесс безопасной выдачи секретов. Они не входят в контекст кабинета
агрегатора. Базовый URL выбирается для реальной юрисдикции аккаунта через
`BYBIT_P2P_API_BASE_URL`; разрешены только перечисленные официальные HTTPS-хосты,
перенаправления запрещены. Менять хост для обхода ограничений нельзя.

Постоянное локальное чтение выполняет отдельный контейнер:

```powershell
./scripts/bybit_quote_worker_windows.ps1 -VaultPath <закрытый-файл-DPAPI> -EnvironmentPath <локальный-env> -Image <собранный-image> -Activate
```

`-Activate` создаёт новую активную версию конфигурации только если предыдущая
неактивна; требуется существующий SuperAdmin. При запуске проверяются права
read-only и P2P Advertising. Ключи передаются через stdin, не Docker Env.
Процесс обновляет общий Redis-кэш и неизменяемые PostgreSQL observations каждые
30 секунд, TTL — 60 секунд. Веб-процесс только читает кэш; ему ключи не передаются.
`BYBIT_P2P_FETCH_IN_PROCESS=false` оставляют в его окружении.

Автоматическое восстановление выполняет supervisor
`scripts/bybit_parser_supervisor_windows.ps1`. Установка штатной задачи владельца:

```powershell
./scripts/bybit_parser_install_task_windows.ps1 -VaultPath <закрытый-файл-DPAPI> -EnvironmentPath <локальный-env> -Image sha256:<проверенный-digest>
```

Задача `OzarkPay-Bybit-ReadOnly` запускается при интерактивном входе владельца,
без сохранения пароля Windows, API Key или Secret в аргументах. Текущий DPAPI
CurrentUser расшифровывается в памяти дочернего процесса, пара передаётся stdin.
Supervisor ждёт доступности Docker и пересоздаёт только свой остановленный
контейнер с проверенной меткой, сетью и закреплённым образом. Mutex исключает
дублирующий запуск. Docker/WSL и другие проекты он не перезапускает.

Docker healthcheck `python -B -m scripts.bybit_parser_health` проверяет свежую
котировку Redis и выводит время последней успешной PostgreSQL observation.
Provider outage делает health unavailable, закрывает финансовое чтение и
повторяется штатным циклом; supervisor не создаёт шторм перезапусков из-за
устаревшей котировки. Историческое время успеха служит диагностикой и никогда
не заменяет финансовую котировку. На выключенном ПК процесс не работает.
Каждая служебная команда Docker supervisor ограничена 15 секундами. Если Docker
подтвердил остановку собственного labelled-контейнера, зависшее дочернее дерево
его launcher завершается перед повторным чтением DPAPI. Процессы чужих проектов
не перечисляются и не останавливаются.

Для остановки автоматики: остановить и отключить указанную задачу, затем
остановить только контейнер parser. Не использовать `docker restart` для worker:
поток stdin с секретом нужно открыть заново из DPAPI. Для Linux/Timeweb нужен
отдельный проверенный процесс выдачи секретов; DPAPI-файл туда не переносится.

## Сторона и порядок

API обозначает сторону объявления: `0` — buy, `1` — sell. Зелёный интерфейс
покупки USDT соответствует продавцам. Само совпадение сторон ещё не подтверждает
совпадение порядка: сайт может показывать отдельную рекламную Featured-карточку
перед обычными объявлениями API. Владелец 18.10.2026 утвердил именно первые три
обычных объявления официального API, без рекламной Featured-карточки. Для этого
подтверждённого контракта сторона запроса и объявлений — `1` (sell), поскольку
пользователь зелёного интерфейса покупает USDT у этих продавцов.
Никакой сортировки, пропуска предложений или фильтров по банкам и суммам нет.

После подтверждения сохраняются исходные позиции 1/2/3, ID, цены, сторона запроса
и объявления, Decimal AVG3, размерность TJS за 1 USDT, время, TTL, версия парсера
и версия конфигурации. Устаревшие, неполные, повторяющиеся и неположительные
котировки отклоняются. Ошибка обновления немедленно закрывает доступ к котировке,
включая прежнее значение в кэше. Сохранённые финансовые snapshots не изменяются.

## Границы готовности

Чтение API, подтверждение зелёного порядка и финансовый Production — разные
состояния. Даже подтверждённая живая котировка не включает TJ-платежи: действующий
backend admission остаётся закрытым. Синтетический курс ручного стенда отдельно
изолирован от живого инфраструктурного источника.

Settlement TJ использует утверждённые USDT TRC20 и комиссию 5 USDT сверх
выплаты; Production остаётся закрытым. Roll переиспользует действующие
подтверждения аванса и FIFO из оплаченных Deposit после индивидуальной комиссии
Merchant, без дополнительной Roll-ставки и без Settlement fee.
Подробности: [TJ Settlement / Roll](tj-settlement-and-roll.md).

Миграция 0043 обобщает название прежнего внешнего процессора. Для существующих
подключений она сохраняет HTTP-диалект в данных и совместимость callback URL;
суммы, ключи, операции и HMAC-канонизация не меняются. Откат используемого старого
диалекта требует восстановления проверенной резервной копии. Timeweb и main
этой разработкой не изменяются.
