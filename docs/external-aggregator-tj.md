# Внешний Aggregator TJ: интеграция и бухгалтерия

Статус реального подключения: **BLOCKED**. Документация конкретного провайдера и
разрешённые ключи не предоставлены. Ни один production-адаптер не зарегистрирован.
Live Bybit Green AVG3, QR и TJ Settle не включены. Эта версия не развёртывается
на Timeweb и не меняет действующие RU/KZ кабинеты.

## Два независимых маршрута

1. Merchant → OzarkPay → внутренний Trader.
2. Merchant → OzarkPay → внешний Aggregator API.

Во втором случае финансовый исполнитель — AggregatorAccount. Deposit не имеет
Requisite внутреннего Trader; отдельные поля financial_executor_type/id и
OperationFeeSnapshot фиксируют единственного исполнителя. Его нельзя заменить
после принятия. Внешние исполнители провайдера не становятся пользователями
OzarkPay. Внутренний Trader не получает ни резерва, ни вознаграждения.

Прежние входящие AggregatorPayment, внутренний Merchant партнёра и его ключи
сохранены. Создание API-интеграции внешнего исполнителя — отдельное явное действие
Admin/SuperAdmin в профиле существующего Aggregator TJ. Старые аккаунты не
получают эту возможность автоматически. Старые скалярные balance/hold_balance
и входящий Merchant-тариф не используются как USDT-залог или ставка исполнения.

## Настройка профиля

Создайте кабинет через действующую форму «Создать кабинет»: Aggregator, TJ,
TJS, подтверждённый идентификатор парсера, C2C и явные лимиты от 10 TJS.
В списке агрегаторов откройте «Профиль / API-интеграция».

Четыре поля предоставляются внешней площадкой:

| Поле | Назначение |
|---|---|
| API Key | Идентификатор авторизации исходящих запросов по контракту площадки |
| Secret Key | Секрет аутентификации исходящего API |
| Webhook ID | Идентификатор подписки/подключения, значение определяется площадкой |
| Webhook Secret | Ключ проверки входящих уведомлений по протоколу площадки |

Webhook ID не является Merchant ID, Deposit ID, Provider Order ID или API Key.
Дополнительно указываются HTTPS Base URL, идентификатор адаптера, версия API,
Sandbox/Production, явный список разрешённых Merchant TJ и IP/CIDR webhook.
Метод пока только C2C. Страна кабинета неизменяема.

Настроенный, ожидающий проверки, проверенный, приостановленный и ошибочный статус
различаются. Заполнение полей не означает успешного подключения. «Проверить
соединение» вызывает только документированную нефинансовую проверку адаптера;
при отсутствии такой проверки результат — «Проверка не поддерживается».
Проверка не создаёт платёж. Разрешение маршрутизации является отдельным действием.
Кнопка QA не разрешает production и требует тариф, обеспечение и список Merchant.

Индивидуальный **тариф исполнителя** хранится как party=aggregator с владельцем
AggregatorAccount.id. Он не подменяет прежний входящий тариф внутреннего Merchant.
Диапазоны начинаются с 10 TJS, не имеют разрывов и должны покрывать максимальный
чек включительно. Пустая сетка не превращается в нулевую ставку.

## Ключи, версии и ротация

Все четыре значения зашифрованы существующим механизмом encrypt_secret;
шифротекст находится в неизменяемой версии конфигурации. Ключ шифрования
предоставляется окружением. После сохранения нет выдачи секретов через HTML/API.
Интерфейс показывает только факт настройки. Пустое поле сохраняет прежнее значение;
каждый параметр можно заменить отдельно. Ключи не включаются в URL, audit details
или диагностические исключения. Изменение требует действующей staff-сессии,
CSRF/Origin, подходящей роли и повторного текущего TOTP.

Ротация запрещена, пока есть prepared/pending/unknown/sending/reconciling или
неразрешённые операции. Сначала сверяются обязательства. Затем создаётся новая
версия, прежняя retired, проверка и routing сбрасываются. Старые webhook после
отзыва версии отклоняются. Поздние уведомления по закрытой/отозванной версии
требуют ручного разбора; история и исходные суммы остаются доступны. Старый
шифротекст сохраняется для аудита, не используется как активный секрет.

Приостановка запрещает отправку и автоматическое применение provider webhook;
залог по неизвестным операциям сохраняется. Это не команда списать/отпустить
обязательства. Возобновление требует проверки, разрешения и текущих условий.

## Merchant API и принятие

Используется существующий POST /api/v1/merchant/deposits с HMAC v2.
Для явно разрешённого агрегаторского маршрута metadata.external_aggregator_id
содержит AggregatorAccount.id. Merchant не может прислать внутренние финансовые
поля, другой executor или подтверждение provider event. Перечень Merchant на
стороне интеграции проверяется сервером; одного ID в запросе недостаточно.

До создания проверяются owner/role/country/currency, HMAC/replay, идемпотентность,
risk, C2C, минимум, оба личных тарифа, фиксированный quote, лимиты Aggregator,
активная проверенная интеграция и доступное обеспечение. PostgreSQL сериализует
лимиты и кошелёк. Одной транзакцией сохраняются Deposit, immutable snapshot,
AggregatorExecution с постоянным external_id и единственный hold. Commit
предшествует исходящему вызову. Provider ID и защищённые внешние реквизиты
добавляются к отдельной записи исполнения, не меняя финансовый snapshot.

POST возвращает pending/состояние обработки. Merchant получает реквизиты через
существующий GET статуса по собственному external_id. До внешнего ответа
реквизиты отсутствуют. Повтор идентичного Merchant-запроса возвращает ту же
заявку, иной запрос с прежней идентичностью отклоняется. Отказ внешнего маршрута
не запускает скрытый fallback на внутреннего Trader или другую площадку.

## Контракт адаптера

AggregatorAdapter задаёт create_payment, get_payment_status, cancel_payment,
validate_webhook, normalize_requisites, normalize_status, verify_connection,
reconcile_payment. Endpoint, payload, подпись, назначение Webhook ID и семантика
подтверждения определяются только документацией конкретной площадки.
Merchant HMAC v2 не переносится на внешний протокол автоматически.

PaymentRequest содержит только постоянный external_id, номинал, TJS, C2C и
callback reference. Ставки Merchant, маржа и внутренние балансы не отправляются.
Конкретный адаптер должен согласовать абсолютный публичный callback URL;
сейчас передаётся относительный callback path изолированной QA.

ProviderResult нормализует external_id, Provider Order ID, amount/currency,
status, допустимые реквизиты и признаки подтверждённого поступления/отсутствия
поступления. HTTP create, включая строку PAID в ответе, не подтверждает оплату.
Для paid нужен проверенный webhook или документированная аутентифицированная
сверка и положительное payment_confirmed. UNKNOWN сохраняет залог.

safe_request — базовый TLS-транспорт для будущего проверенного адаптера:
только HTTPS/443, публичный DNS, запрет адресов IP, userinfo/query/fragment,
localhost/private/link-local/metadata, проверка всех DNS-ответов, соединение с
проверенным IP с исходным TLS SNI/hostname, проверка сертификата, запрет redirects
и proxy environment. Есть ограничение времени/размера, автоматического retry нет.
Имя approved_host задаёт проверенный адаптер, а не Merchant. Перед добавлением
реальной площадки необходимы аудит allowlist/egress и протокола аутентификации.
Это транспортный примитив, не готовый универсальный API площадок.

## Webhook

POST /api/v1/external-aggregators/{integration_version_id}/webhook изолирован от
Merchant и старого входящего Aggregator API. UUID версии — публичный идентификатор,
не секрет. Адаптер сначала проверяет подпись точного тела и контрактные поля.
Затем общий сервис проверяет Webhook ID, timestamp, event ID, версию, исполнителя,
external_id/Provider Order ID, номинал, TJS и допустимый переход. По контракту
поддерживаются дополнительные IP/CIDR. Размер тела ограничен. Действует общее
Redis rate limiting; event deduplication сохраняется в PostgreSQL.

Подписанные события сохраняются как hash + нормализованная принадлежность/статус,
без сырых заголовков с секретами. Повтор одинакового события идемпотентен;
одинаковый event ID с изменённым существенным содержимым требует manual_review.
Событие другого аккаунта/версии не может подтвердить чужую заявку. Повтор paid
не создаёт второй debit/credit. Противоречие после paid сохраняет уже проведённые
активы и требует сверки. Запоздалый paid после отмены не списывает доступное
обеспечение автоматически: требуется существующий ручной appeal-процесс.

## Durable outbox, сбои и retry

AggregatorExecution является устойчивым намерением отправки. Worker получает
lease/token под короткой блокировкой, фиксирует sending и attempt, освобождает
транзакцию, выполняет сеть и отдельной транзакцией применяет результат.
Финансовые блокировки не удерживаются во время HTTP.

| Состояние/сбой | Действие |
|---|---|
| prepared, ещё не отправляли | Один create с постоянным external_id |
| worker умер до/после отправки | После lease — lookup/reconcile, без слепого create |
| Timeout / 500 / 429 / некорректный ответ | UNKNOWN, backoff и сохранённый hold |
| Документированное RequestNotSent | Безопасный повтор с прежним external_id |
| Авторитетное отсутствие + idempotent create | retry_safe с прежним external_id |
| Lookup/idempotency не подтверждены | manual_review, залог не отпускается |
| Восемь неудачных попыток | manual_review с сохранением обязательства |
| Webhook до create-response | Тот же order; lease fencing не позволяет позднему ответу отменить paid |
| Pending | Повторная сверка с задержкой, без нового создания |

Восстановление выбирает только due/неарендованные записи ограниченными порциями.
Новые и очередные due-записи не должны вытесняться постоянно перечитываемыми
pending. Существующий Celery содержит отдельную recovery-задачу; обычный запуск
production закрыт. QA worker получает внешнюю dependency вне образа.

## Математика и ledger

Decimal / ROUND_HALF_UP; сначала комиссия в TJS (2 знака), затем остаток в USDT
(8 знаков). R — TJS за 1 USDT из зафиксированного bybit_p2p_tjs_green_avg3.

    MerchantFeeTJS = round(A*M/100, 2)
    ExecutorFeeTJS = round(A*E/100, 2)
    BaseUSDT = round(A/R, 8)
    ReserveUSDT = DebitUSDT = round((A-ExecutorFeeTJS)/R, 8)
    MerchantCreditUSDT = round((A-MerchantFeeTJS)/R, 8)
    PlatformMarginUSDT = DebitUSDT - MerchantCreditUSDT

M<E или отрицательная маржа отклоняются без скрытого обнуления. Индивидуальные
ставки не имеют общего fallback. В snapshot фиксируются обе версии планов,
источник/версия quote, все суммы, округления и версия API-интеграции.
Арифметика прямого Trader TJ сохранена. Из неё переиспользованы расчёт context,
общая collateral arithmetic, Merchant credit/fee, platform income, refund,
lifecycle, ручной appeal и исходящий Merchant webhook outbox.

Синтетический пример: A=1090, R=10.90, M=10%, E=7%:
Base=100; hold/debit=93; Merchant=90; margin=3 USDT. Эти ставки не являются defaults.

| Переход | Aggregator balance / hold / available | Merchant | Margin |
|---|---|---|---|
| QA opening | 1000 / 0 / 1000 | 0 | 0 |
| pending | 1000 / 93 / 907 | 0 | 0 |
| paid | 907 / 0 / 907 | 90 | 3 |
| accounting refund | 1000 / 0 / 1000 | 0 | 0 |
| подтверждённая no-credit отмена | 1000 / 0 / 1000 | 0 | 0 |
| UNKNOWN / неподтверждённый TTL | 1000 / 93 / 907 | 0 | 0 |

Trader во всех строках агрегаторского сценария неизменен. Отдельного бонуса
Aggregator или начисления его внутренним трейдерам нет. TJS — внешний номинал и
оборот, он не создаётся вторым spendable активом при получении Merchant USDT.
Refund — точный бухгалтерский inverse с проверкой available Merchant; не
банковский возврат клиенту и не вызов внешнего refund API.

## БД, сверка и ограничения среды

Новая ревизия: 0042_external_aggregator после 0041_tj_history_references.
0038–0041 не переписаны. Добавлены versioned integration, independent wallet /
append-only journal, durable execution и provider events. Существующие FeeRule,
TariffPlan, OperationFeeSnapshot и Deposit расширены, а не продублированы.

PostgreSQL проверяет одного исполнителя, immutable identity, страну/кошелёк,
тариф/quote, запрет чужого journal и deferred равенство reserve/debit/credit/margin.
Баланс Aggregator проверяется по сумме journal. При paid/refund совпадают все
стороны; прямые Trader entries у агрегаторской операции запрещены. Сервисная
reconciliation независимо пересчитывает баланс/hold из сумм движений; Merchant
проверяется существующей reconciliation, без доверия к after-values.

Для любых TJ-проводок по-прежнему нужны одновременно ENV=test, внешний callable
quote, БД с префиксом ozark_tj_wave3_, роль ozark_tj_test и transaction-local marker.
Внешнему маршруту дополнительно нужна внедрённая QA factory адаптера и sandbox.
Подстановка из HTTP body или один env flag это не открывают. Это защита от ошибки
конфигурации, не от администратора, который может менять DDL/код.

Mock-площадка — отдельный HTTP-контейнер QA с отдельным протоколом подписи,
состоянием заказов и ошибками/timeout. Её код, ключи, adapter factory, datasets,
tests, чеки и дампы исключены из production image, публичного Git и source ZIP.
Тест HTTP в изолированной сети не считается проверкой TLS/реального провайдера.

## Внедрение и откат

1. Получить спецификацию, назначение Webhook ID, схемы подписей/nonce/replay,
   авторитетного lookup, идемпотентности, timeout/cancel/refund и форматов реквизитов.
2. Реализовать и независимо проверить конкретный адаптер и сетевой allowlist.
3. Подтвердить live Bybit side/units/Green AVG3/TTL и политики сверки/риска.
4. Получить отдельное разрешение на production, проверить backup через restore,
   квоты/секреты, миграции, финальную регрессию и ограниченный sandbox rollout.
5. Только после независимого аудита планировать отдельное окно Timeweb.

Downgrade допускается только для неиспользованного расширения. При интеграциях,
тарифах или истории исполнения он отказывается: конфигурация/ключи/обязательства
не уничтожаются. После операций закрывают admission/dispatch, сохраняют схему,
сверяют внешние заказы и разворачивают совместимый исправленный образ. Нельзя
делать stamp, стирать историю или слепо восстанавливать старый backup: внешний
провайдер мог принять операции после его создания. Restore — отдельный recovery
план с учётом всех новых обязательств.
