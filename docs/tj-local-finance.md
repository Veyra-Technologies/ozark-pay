# TJ → TJ · Wave 3 · финансовая адаптация существующего Deposit

**Реальный приём TJ закрыт.** В штатном приложении нет тестового источника курса
или флага, открывающего приём. Успешные финансовые сценарии допускаются только
при внешней dependency injection в изолированном QA, одновременно ограниченном
сервисом и PostgreSQL. Timeweb/main и Production Transferio RU/KZ эта Wave не меняет.

## Переиспользование RU → RU

| Этап | Существующая архитектура RU | Валютная адаптация TJ |
|---|---|---|
| Создание | Merchant API, HMAC v2, replay, idempotency/external_id, risk | Те же обработчики; только Merchant TJ, TJS, C2C от 10 TJS; serial lock кабинета |
| Комиссии | FeeRule → immutable OperationFeeSnapshot | Личный утверждённый TariffPlan; неактивная FeeRule-ссылка на его ступень; нет общих/default ставок |
| Назначение | select_deposit_requisite, blacklist, traffic, limits, locks | Тот же selector, TJ банк/владелец/валюта, личный тариф Trader, отдельное USDT-обеспечение |
| Резерв | metadata hold + ledger, атомарное назначение | TraderWallet/TraderWalletLedgerEntry в USDT, 8 знаков; legacy RUB User balance не используется |
| Подтверждение | confirm_deposit_payment, Deposit lock, audit, outbox | Проверенные сумма, реквизит, время, выписка и полномочия; USDT debit/credit/margin |
| Отмена | finalize_unsuccessful_deposit, release | Неизвестное поступление удерживает резерв; release только после авторизованной отрицательной сверки |
| Апелляция | Существующие Appeal, чек, owner scope, review | Фиксированный реквизит, TJS-сумма, время; решение Admin/SuperAdmin; без timer autoapproval |
| Возврат | Deposit lifecycle/audit/outbox; статус refunded уже есть в домене | Точная обратная проводка исходного расчёта; отдельный подтверждённый staff-запрос |
| Callback | Существующий подписанный outbox, delivery claim/retry | Сохраняет event_id; TJ требует QA-инъекции транспорта, реальная внешняя доставка закрыта |
| Сверка | Merchant journal/balance reconciliation | Отдельная USDT-сверка Merchant, независимая сумма движений Trader, USDT-маржа платформы |

`local_deposit_policy.py` задаёт валютные правила существующего Deposit. Он не
создаёт заявки, маршруты, таймеры, собственный outbox или параллельный lifecycle.
Generic ledger-функции получили явную валюту с прежним RUB по умолчанию.
Legacy глобальные денежные лимиты имеют RUB-размерность и не становятся TJS
посредством замены строки. TJ использует собственные лимиты реквизита/Trader и
Merchant-scoped risk rules, сохраняя blacklist, velocity и ограничения количества.

## Формулы и точность

`A` — номинал TJS; `R` — зафиксированные TJS за 1 USDT; `m/t` — проценты личных
утверждённых планов Merchant/Trader. Проценты не имеют начальных значений.
Все операции выполняются через Decimal с ROUND_HALF_UP.

```
feeM_TJS = round(A × m / 100, 2)
feeT_TJS = round(A × t / 100, 2)
BASE_USDT = round(A / R, 8)
reserve = debit = round((A − feeT_TJS) / R, 8)
MerchantCredit = round((A − feeM_TJS) / R, 8)
PlatformMargin = debit − MerchantCredit
feeM_USDT = round(feeM_TJS / R, 8)
feeT_USDT = round(feeT_TJS / R, 8)
```

Сначала округляется локальная комиссия, как в RU. Суммы debit/credit считаются
непосредственно из локального остатка; нельзя получать их вычитанием отдельно
округлённых USDT-эквивалентов. Возможные расхождения в одну минимальную единицу
записаны отдельными rounding_delta в snapshot. Маржа равна фактическому debit
минус фактический credit. Merchant-процент ниже Trader-процента отклоняется.

**Только синтетический пример QA; это не производственные ставки и не live-курс:**
цены 10.80, 10.90, 11.00 дают R = 10.90; явно заданные m = 2%, t = 1%.

| Номинал | BASE_USDT | feeM TJS | feeT TJS | Резерв/списание USDT | Merchant USDT | Маржа USDT |
|---:|---:|---:|---:|---:|---:|---:|
| 1 090.00 TJS | 100.00000000 | 21.80 | 10.90 | 99.00000000 | 98.00000000 | 1.00000000 |
| 10.00 TJS | 0.91743119 | 0.20 | 0.10 | 0.90825688 | 0.89908257 | 0.00917431 |

TJS поступает на внешний банковский реквизит Trader. Это банковский номинал,
оборот и локальная база комиссии, а не второй автоматически созданный актив
OzarkPay. Отдельный TJS-кошелёк кабинета сохраняется, но конвертация не зачисляет
в него фиктивные деньги. Доход Trader — сохранённая часть банковского номинала /
уменьшенное списание обеспечения; повторного зачисления «прибыли USDT» нет.

## Матрица состояний и полномочий

| Переход | Основание/роль | Состояние | Финансовый эффект |
|---|---|---|---|
| Создание | Собственный Merchant HMAC v2, курс и оба личных плана, лимиты/обеспечение | pending | Один reserve USDT, фиксированные quote/plans/requisite |
| Ручное поступление | Назначенный активный Trader или Admin/SuperAdmin; точная сумма/реквизит; aware время после создания и не в будущем; номер выписки и явная сверка | paid | Один debit резерва, один Merchant credit и margin |
| Запрос отмены / TTL, банковский результат неизвестен | Existing lifecycle | appeal_opened, bank_result_unknown | Резерв остаётся; paid автоматически не наступает |
| Проверено отсутствие поступления | Назначенный Trader / Admin/SuperAdmin, основание и номер сверки; нет открытого спора/положительного подтверждения | failed/cancelled/expired по вызвавшему переходу | Один release, основная сумма кошелька не меняется |
| Апелляция | Merchant по собственной операции, назначенный Trader, точные TJS/банк/карта и aware время, сохранённый чек | appeal_opened | Денежных зачислений нет |
| Одобрение апелляции | Только Admin/SuperAdmin после ручной проверки доказательств | paid | Fixed расчёт; debit резерва или доступного обеспечения после прежнего release; недостаток отклоняется атомарно |
| Бухгалтерский возврат | Admin/SuperAdmin, действующая 2FA, основание/номер решения; paid, нет открытого спора | refunded | Точный inverse при доступных активах Merchant |
| Повтор confirm/refund/cancel | Та же операция и допустимая идентичность | Сохранённый результат | Повторных денежных движений нет |

Одобрение апелляции по таймеру TJ запрещено; запрос автоматической обработки
исключает TJ, чтобы его споры не задерживали RU. Прямое подтверждение во время
активного спора запрещено. Файлы не удостоверяют банковский перевод сами по себе:
проверка magic/размера/владельца, реквизита, суммы и времени лишь подготавливает
ручное решение сотрудника. Банковского API или проверки подлинности выписки нет.
Бухгалтерский возврат не делает банковский перевод клиенту.

## Матрица проводок и сверка

Пусть исходное обеспечение Trader = 1000 USDT, пример A = 1090 TJS как выше.
`balance` включает `hold`, `available = balance − hold`.

| Действие | Trader balance/hold/available USDT | Merchant available USDT | Platform USDT |
|---|---|---:|---:|
| Открытие QA через adjustment journal | 1000 / 0 / 1000 | 0 | 0 |
| pending, hold 99 | 1000 / 99 / 901 | 0 | 0 |
| paid, debit hold 99 | 901 / 0 / 901 | 98 | 1 |
| inverse paid → refunded | 1000 / 0 / 1000 | 0 | 0 |
| Вместо paid — отрицательная сверка и release | 1000 / 0 / 1000 | 0 | 0 |
| Поздняя успешная апелляция после release | 901 / 0 / 901 | 98 | 1 |

Merchant credit/refund и platform margin/refund имеют USDT-размерность. TJS fee и
executor_fee — информационный учёт локальных комиссий; они не увеличивают
spendable TJS-актив. Reconciliation разделяет валюты. `local_refund` уменьшает
available Merchant, не расходуя чужие замороженные обязательства.

Существующий сводный отчёт доходов RU явно ограничен RUB-snapshot и RUB-journal:
локальные комиссии TJS не складываются с рублями, а USDT-маржа TJ не сравнивается
с рублёвыми суммами. Валюта отчёта показана в UI и API. Статистика TJ и его
фактические USDT-проводки сверяются отдельно по кабинету и операции.

Блокировки идут в порядке Deposit → TraderWallet → Merchant Balance. Для
назначения также используются существующие locks реквизитов и Merchant serial
advisory lock. Баланс/резерв проверяются под блокировкой, journal idempotency
защищён уникальным ключом, все проводки и изменение состояния атомарны.

## Snapshot и изоляция

Сохраняются три исходные цены и ID объявлений/позиции, среднее, подтверждённая
тестовая сторона/размерность, config/observation/version/time/TTL, явно синтетическое
происхождение, оба личных плана/ступени, номинал, комиссии, база, reserve/debit/
payable/margin/rounding и зашифрованный реквизит. RateObservation и финансовый
snapshot неизменяемы. API/status/повтор/апелляция используют принятые данные,
новый курс/тариф или последующее изменение карты не переоценивают заявку.

Merchant получает только собственные финансовые поля: тарифы Trader, маржа и
зашифрованные реквизиты не включаются в его API или callback. Участники видят
свои операции и историю; технические балансы RU/KZ/GE не используются для TJ.
Один кабинет — одна страна, отдельные входы/ключи/wallet/journal scope.

## Aggregator — BLOCKED для неопределённого исполнения

RU Aggregator — входящий партнёр со своим AggregatorAccount, внутренним Merchant,
клиентами, ключами и комиссией, направляющий входящий поток реальным Trader.
У него нет утверждённого исполнения собственным реквизитом/USDT-залогом Trader.
TJ сохраняет эту роль, личный тариф и отдельные TJS/USDT-балансы. Его inbound
финансовый приём и роль исполнителя блокируются до утверждения контракта.
Подмена роли Aggregator на Trader или перенос его ставки в Trader запрещены.
Это ограничение соответствует разделу 6 задания Wave 3; положительная финансовая
приёмка данной Wave использует реального Trader, а не вымышленную модель Aggregator.

## Live Bybit / QR / Settle — BLOCKED

Доступ General Advertiser/P2P API отсутствует по подтверждению владельца.
Реальный порядок первых трёх зелёных предложений и соответствие UI/API стороны
не подтверждены. Нельзя заменять источник Rapira/Binance, угадывать side,
подменять units или обходить допуск Bybit. Транспорт и нормализация Wave 2 сохранены;
успешная синтетическая QA-проверка не подтверждает live Bybit или реальный банк.

QA-провайдер находится только за пределами приложения/образа/source ZIP.
Сервис требует ENV=test, внешний callable в DB dependency, точный DB-prefix
`ozark_tj_wave3_` и роль `ozark_tj_test`. PostgreSQL независимо требует тот же
database/role и transaction-local marker. Один environment flag не открывает приём.
Это несколько защит от ошибочной активации, не граница против администратора БД,
способного менять код/DDL. В обычной production-конфигурации приём закрыт.

TJ callbacks дополнительно требуют явно переданного QA HTTP transport; fixture
503→200 проверяет подписанный outbox/retry и защиту повторной доставки без реальной
сети. Worker/beat в финансовом QA не запускаются. QR и TJ Settle не активированы;
комиссия 5 USDT, вывод/rolling или новые платёжные способы не наследуются из RU/KZ.

## Миграции 0040/0041 и план внедрения

0040 следует за опубликованными неизменёнными 0038/0039. Добавляет nullable FK
FeeRule → country TariffPlan и nullable JSON финансового context, независимый
admission guard, scope/append-only journal guards и deferred проверку полноты
TJ-проводок на commit. Старые balances/keys/journals не пересчитываются.

0041 дополнительно сохраняет старую принадлежность journal при UPDATE: изменение
operation_id не обходит append-only guard. Она запрещает удаление TJ Deposit и
snapshot, изменение принятой суммы/владельца/реквизита/идентификаторов и добавляет
deferred сверку при изменении settlement-полей snapshot. Миграции не меняют старые
проводки. Отсутствующий context в ORM сохраняется как SQL NULL, сохраняя RU-пути.

1. Сохранить восстановимую резервную копию, inventory и контрольные суммы.
2. Восстановить её в отдельный QA PostgreSQL; проверить версию 0039 и старые строки.
3. Выполнить `alembic upgrade head`, сравнить все таблицы с учётом только новых NULL
   колонок/revision, выполнить полный regression на окончательном образе с Redis.
4. Выполнить browser acceptance и независимую сверку записанных движений.
5. Оставить PR Draft и production TJ admission закрытым. Эта Wave не разрешает
   внедрение на Timeweb. Для будущего production rollout необходим отдельный план,
   live-source contract, policies и отдельное разрешение владельца.

## План отката

На копии без TJ финансовой истории `alembic downgrade 0039_tj_bybit_individual`
штатно снимает новые guards/nullable поля; после проверки возможен повторный
upgrade. `alembic stamp` не используется. После появления TJ snapshots/adapter
rows/платежей downgrade **защищённо запрещён**, чтобы не потерять обязательства.
Применять совместимый forward rollback: закрыть вход/остановить QA-инъекцию,
сохранить schema/history, сверить кошельки, поставить исправленный совместимый
образ. Нельзя откатывать миграцию с удалением финансовой истории или обнулять
кошельки. Restore допустим только отдельным согласованным recovery-планом с
учётом всех операций после точки резервной копии.

Source ZIP не содержит tests/demo, QA harness, синтетическую БД/чеки, ключи,
пароли/2FA, .git или .env с секретами. Локальные журналы/JUnit/скриншоты и подробный
отчёт хранятся отдельно; результат каждого прогона указан в отчёте, без подмены
целевых тестов итоговым полным regression.
